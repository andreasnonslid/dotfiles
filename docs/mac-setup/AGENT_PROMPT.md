# Scheduled agent run protocol

This is the full protocol for a scheduled run against the Mac setup backlog. The Routine
prompt is a short bootstrap that points here; this file is the authority. Edit it freely —
changes take effect on the next run without touching the Routine.

## The one rule that matters most

**Do exactly one deliverable, then stop.**

Not "one deliverable plus a small related fix". Not "two, because the second was easy".
One. The backlog is ordered by dependency and sized so each item is reviewable on its own.
Batching destroys that and makes a bad change hard to isolate.

If you finish early, stop early. Ending a run with one clean, verified deliverable is the
success condition.

---

## 1. Orient

```sh
git fetch origin claude/mac-work-setup-gchgxr
git checkout claude/mac-work-setup-gchgxr
git pull origin claude/mac-work-setup-gchgxr
```

Read `docs/mac-setup/BACKLOG.md`. It is the source of truth for what is done and what is
next.

## 2. Select

Pick the **first unchecked item whose dependencies are all ticked**.

Skip an item if:

- it is tagged `needs-mac` — those are validated by the user on hardware, not by you
- its GitHub issue already has an unresolved claim comment from another run
- it is **M24**, unless the user has explicitly asked for it in this session (see Special
  cases below)

If every remaining item is blocked, say so plainly and stop. Do not invent work, and do
not start something out of order because it looks easy.

## 3. Claim

Comment on the item's GitHub issue that you are starting. Look up the issue number in the
index table at the top of `BACKLOG.md`.

This exists so overlapping runs do not collide. Check for an existing claim before adding
yours.

## 4. Implement

Work on branch `claude/mac-work-setup-gchgxr`. Never push to `master`.

Scope yourself to the item's acceptance criteria. If you spot an unrelated problem, note
it in the issue close-out comment for a future item — do not fix it now. Out-of-scope
fixes are the most common way a one-item run turns into an unreviewable diff.

### You cannot test on macOS

You are in a Linux container. Everything you write for macOS is unverifiable here, so:

- Write it to be **statically** verifiable — syntax-checkable, shellcheck-clean, unit
  testable against a fake `$HOME`
- If the item introduces something a real machine could get wrong, **add a matching check
  to `scripts/doctor.d/`**. This is a standing requirement, not optional.
- If the item is `needs-mac`, append its verification steps to `macos/RUNBOOK.md`
- Never claim something works on macOS. Say what you implemented and what remains
  unverified.

### Match the existing code

Read neighbouring files before writing. Match their comment density, naming and idiom.
This repo has clear conventions — 4-space indent, 80 columns (`.editorconfig`), `wfn`
registration for discoverable shell functions, guard clauses over nesting.

## 5. Verify

```sh
./scripts/check.sh
```

**Must pass.** If it does not exist yet (M02 has not landed), verify by hand with whatever
is available — `bash -n`, `python3 -m py_compile`, `prettier -l` — and say in the issue
comment exactly what you were able to check and what you could not.

Markdown is formatted by `prettier` via `pretty.lua`, so run `prettier --write` on any
`.md` you touch or the pre-commit hook will reject it.

## 6. Commit

`.githooks/commit-msg` enforces conventional commits. The constraints are tighter than
usual and rejection is silent-ish, so get them right first time:

- Format `<type>(optional-scope): <summary>`
- Types: `feat fix docs style refactor perf test build ci chore revert`
- Type lower-case and required; scope optional, lower-case, no spaces
- **Summary: 2–10 words AND 10–50 characters**
- **Header: max 72 characters**

Body should say what changed and why. End with:

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

## 7. Push

```sh
git push -u origin claude/mac-work-setup-gchgxr
```

On network failure only, retry up to 4 times with backoff (2s, 4s, 8s, 16s).

**Do not open a pull request.** The user will decide when to open one.

## 8. Close out

- Tick the item's checkbox in `BACKLOG.md` and update the `Progress: N / 45` count
- Commit that update (it can go in the same commit as the work)
- Close the GitHub issue with a short comment covering: what changed, anything that could
  not be verified, and anything the next agent should know
- End every GitHub comment with:

```
---
_Generated by [Claude Code](https://claude.ai/code)_
```

## 9. Stop

Do not pick up another item.

---

## When something is wrong

If an item turns out to be mis-scoped, blocked by a bad assumption, or dependent on
something that does not exist — **do not improvise around it**.

Comment on the issue explaining precisely what is wrong and what you would suggest
instead. Leave the checkbox unticked. Stop. A clear "this item is wrong because X" is a
more useful run than a clever workaround nobody asked for.

The same applies if an acceptance criterion turns out to be impossible to verify in the
container: say so rather than ticking it on faith.

## Special cases

**M24 (migrate Linux distro scripts to mise)** is the one item that can break a machine in
daily use — it rewrites the provisioning scripts for working Linux boxes. Everything else
in this backlog builds something that does not exist yet.

Do not tick M24 on static checks alone. Implement it if selected, push it, then explicitly
flag in the issue that it needs user smoke-testing on a real Linux machine before the box
is ticked, and leave the box unticked.

**M19 (AeroSpace config)** contains a real design decision — SUPER→Cmd vs SUPER→Alt. Make
the call, but document the tradeoff in a comment in the config rather than silently
picking one.

**M36** is the final reconciliation and depends on hardware. Do not attempt it until the
user has run the RUNBOOK and provided `doctor.sh --json` output.
